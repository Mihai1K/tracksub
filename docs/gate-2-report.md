# Gate 2 — отчёт

Дата: 04.09.2026. Статус: **закрыт на синтетике**. Конвейер и движок атрибуции построены,
покрыты тестами и прогнаны на сценарии из 23 событий. Реальными данными платформы не проверено
ничего — это по-прежнему блокировано доступом (см. Gate 1, §3).

---

## 1. Что проверено

- Собран конвейер `сырое → нормализованное → домен → атрибуция` по решению из `architecture.md`.
- Написан сценарий из **23 событий** (`fixtures/scenario.js`), покрывающий все случаи из протокола §14:
  дубль доставки, отсутствующие поля, невалидный JSON, ретрай, две подписки, отписка, повторная
  подписка, несколько кампаний, конфликт источников, границы окна, таймзоны.
- **37 тестов** (`node --test`), из них 16 — на движок атрибуции.
- Прогон сценария через реальный конвейер: `node tools/replay.js`.
- Отдельно проверено, что запрос с неверным секретом не доходит до хранилища.

## 2. Что подтверждено

| Свойство | Как проверено |
|---|---|
| Идемпотентность входа | Повторная доставка того же события: одна запись `webhook_events`, одна подписка |
| Сырое не теряется | Невалидный JSON и событие без `timestamp` сохранены целиком, помечены `failed`, доступны для повторного прогона |
| Ретрай безопасен | Повторная обработка успешного события не создаёт дублей в домене |
| Точная схема | `bot_started(payload)` + общий `user_id` → `deterministic`, уверенность 1.0 в окне 60 мин, 0.8 до 24 ч, дальше — откат на вероятностную |
| Приоритет сигналов | Детерминированный кандидат побеждает более свежий вероятностный |
| Два payload | Побеждает последний, подписка помечается `is_ambiguous` |
| Чужой payload | Не расшифровывается в наш клик → точной атрибуции не даёт |
| Вероятностная схема | Скор по §7, `confidence`, `margin`, все кандидаты сохраняются |
| Плотный поток | Более 20 кандидатов → `is_dense`, уверенность вдвое ниже, подписка помечается неоднозначной |
| Отписки | `admin_id = null` → `left`; иначе `removed`, в отток не идёт |
| Повторная подписка | Внутри 7 суток → `is_resubscribe`, вне — полноценная новая |
| Пересчёт | Повторный пересчёт из сырых данных даёт тот же результат; старые версии атрибуции не удаляются |
| Таймзона | Хранение и сравнение в UTC: workspace в UTC и во Владивостоке дают идентичную атрибуцию |
| ПДн | Сырой IP не хранится, только 24-символьный хеш с солью |

### Два дефекта, найденных тестами и исправленных

1. **Атрибуция зависела от порядка обработки.** Множитель `freshness` (§7) смотрел на любые другие
   атрибуции, включая более поздние. Из-за этого пересчёт из сырых данных давал каждый раз новый
   ответ. Исправлено: «уже атрибуцирован» теперь означает «атрибуцирован к более ранней подписке»,
   порядок фиксирован по `(ts_utc, id)`. Пересчёт стал детерминированным — на это есть тест.
2. **Дедуп кликов глушил живых людей.** Окно 30 секунд сравнивалось со всеми кликами, включая
   отфильтрованные. Бот, дёргающий ссылку раз в 20 секунд, бесконечно продлевал окно и отбрасывал
   клики реальных пользователей с тем же IP и UA. Исправлено: сравнение только с засчитанными.

### Одно осознанное отступление от спецификации

`attribution.md` §7 требует множитель `device_match` — сравнение `device_hint` клика с устройством
события. **События MAX не содержат никаких признаков устройства** (FACT: `UserAdded` = `inviter_id`,
`chat_id`, `user`, `is_channel`). Сравнивать не с чем. Реализовано как штраф 0.85 только для кликов,
по которым устройство не определено вовсе. Отступление помечено в коде (`src/attribution.js`,
`deviceMatch`) и подлежит пересмотру, если платформа начнёт отдавать признак устройства.

## 3. Что не подтверждено

Главное: **ни одно событие настоящего MAX через этот конвейер не прошло.** Формы событий взяты из
моделей официально проверенной библиотеки, но это не замена эксперименту.

1. E1–E8 из `gate-1-experiment.md` по-прежнему не выполнены. Открыты те же вопросы: приходит ли
   `user_added` при самостоятельной подписке, приходит ли `bot_started` повторно, какова реальная
   задержка доставки и политика ретраев платформы.
2. Точность вероятностной схемы. Прогон показывает `accuracy = 100%` — **эта цифра ничего не значит**:
   в синтетике детерминированный клик заодно оказывается и ближайшим по времени. Настоящая калибровка
   возможна только на живом трафике (§12), и до неё никакое число точности не идёт в маркетинг.
3. Поведение под нагрузкой, пагинация `GET /chats/{chatId}/members`, лимиты 30 rps.
4. Хранилище: сейчас SQLite — этого достаточно для разработки и тестов, но не для продакшена.
   Слой доступа изолирован (`src/db.js`), миграция на Postgres — работа на день, но она не сделана.

## 4. Что является риском

| Риск | Влияние | Что делаем |
|---|---|---|
| Поток и пересчёт дают разные ответы | В потоке ещё не известны более поздние сигналы, поэтому первая атрибуция провизорная. Пользователь может увидеть, как цифра «поехала» | Показывать в интерфейсе, что данные суток дозревают; авторитетным считать ночной пересчёт. Инвариант «пересчёт идемпотентен» закреплён тестом |
| Дедуп 30 секунд за одним NAT | Два разных человека с одинаковым UA из одной сети в пределах 30 секунд схлопнутся в один клик | Принято как допустимая потеря; при жалобах — сузить окно или добавить cookie-сигнал |
| Синтетический ключ идемпотентности | Два настоящих одинаковых события в одну миллисекунду схлопнутся | Принято (`attribution.md` §11). Если E-эксперимент покажет собственный ID события — заменить |
| Вся валидация на синтетике | Может рассыпаться о реальность | Не строить Gate 3 до E1 |
| SQLite в продакшене | Блокировки при конкурентной записи | Postgres до первого платящего клиента |

## 5. Что предлагаю сделать

**Не начинать Gate 3.** Дашборд — это витрина над данными, которых мы ещё ни разу не видели живьём.
Правильный следующий шаг тот же, что и на выходе из Gate 1: получить доступ и прогнать E1–E8.
Стенд для этого уже есть (`probe/`), а теперь есть и конвейер, который примет реальные события
без переделки.

Если доступ появится — порядок такой:

1. E1: приходит ли `user_added` при самостоятельной подписке. Один час, решает судьбу схемы Б.
2. E4: повторный `bot_started`. Решает, нужен ли fallback через `message_callback`.
3. Прогнать 50–100 реальных событий через `pipeline.handleIncoming` и сравнить с ожидаемым.
4. Первая честная калибровка (§12) — и только после неё любые цифры точности где-либо.

## 7. Как проверить результат

```bash
npm test          # 37 тестов, все зелёные
npm run replay    # прогон 23 событий: доставка, счётчики, атрибуция, калибровка, пересчёт
```

В выводе `replay` смотреть на три вещи: `дубль (idempotent)` у события E-03, `failed` у E-11 и E-23
при сохранённом сыром теле, и строку «пересчёт идемпотентен: да». Строка «поток == пересчёт: нет» —
ожидаемое поведение, объяснено в §4.
