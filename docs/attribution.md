# Attribution spec

Формальное описание атрибуции. Написано **до** кода. Всё, что зависит от неподтверждённых
возможностей платформы, помечено ссылкой на эксперимент в `gate-1-experiment.md`.

Принцип, который не обсуждается: **вероятностная атрибуция никогда не выдаётся за точную**.
Тип и уверенность хранятся в данных и показываются в интерфейсе.

---

## 1. Событие «клик»

Клик — HTTP-запрос к нашему redirect-endpoint `/r/{link_slug}`, прошедший фильтры.

Записываем: `click_id` (16 символов `[A-Za-z0-9_-]`, генерится нами), `tracking_link_id`, `ts_utc`,
`ip_hash` (соль + SHA-256, сырой IP не храним), `user_agent`, `referer`, все query-параметры
(`utm_*`, `yclid`, `gclid`, `vk_click_id` и произвольные), `platform_target` (max | telegram),
`redirect_mode` (bot | direct), `device_hint` (ios | android | web | unknown, из UA).

**Не считается кликом** и пишется со статусом `filtered`:
- HEAD-запросы и запросы известных ботов/сканеров по UA;
- префетч рекламных сетей (эвристика: нет `Accept: text/html`, либо UA содержит `preview`/`bot`);
- повтор с тем же `ip_hash + user_agent + tracking_link_id` в пределах **30 секунд** — дедуп по клику;
- запросы без валидного `tracking_link_id`.

Отфильтрованные клики хранятся, но не участвуют ни в метриках, ни в атрибуции.

## 2. Событие «подписка»

Подписка — `user_added` с `is_channel = true` для канала, подключённого к workspace.

`subscription_event`: `platform`, `chat_id`, `platform_user_id`, `ts_utc` (из `timestamp` события),
`ts_received_utc` (когда получили мы), `inviter_id`, `raw_event_id`.

Отдельно фиксируется `bot_start_event` (`bot_started`): `platform_user_id`, `payload`, `ts_utc`.
Это **не** подписка. Это сигнал источника.

**Зависимость:** приходит ли `user_added` при самостоятельной подписке на публичный канал — `E1`.
Если нет, схема Б (§7) не существует, и продукт работает только через бот-прокладку.

## 3. Событие «отписка»

Отписка — `user_removed` с `is_channel = true`.
`admin_id = null` → пользователь ушёл сам (`reason = left`).
`admin_id != null` → удалён администратором (`reason = removed`).

В retention учитывается **только `left`**. Удаление админом исключает подписчика из когорты
(и из знаменателя), а не считается оттоком: иначе чистка ботов владельцем канала испортит нам метрику.

## 4. Окно атрибуции

- **Окно точной схемы** (`bot_started` → `user_added`): **60 минут**. Пользователь пришёл в бота
  и подписался в том же сеансе. Больше — подозрительно, но допустимо: до **24 часов** с понижением
  уверенности.
- **Окно вероятностной схемы** (клик → `user_added`): **72 часа**, по умолчанию.
  Настраивается на workspace в диапазоне 1–168 часов.
- **Технический допуск на задержку доставки**: клик, случившийся до 120 секунд *после* timestamp
  подписки, тоже считается кандидатом — расхождение часов и задержка webhook. Величина уточняется
  после `E2` (измерение реальной задержки).

Всё хранится в UTC. Отображение — в таймзоне workspace. Границы суток в отчётах считаются
по таймзоне workspace, агрегаты пересчитываются при её смене.

## 5. Модель выбора источника

Базовая модель — **last click within window**, с приоритетом типа сигнала:

1. `deterministic` — есть `bot_started` с валидным `payload`, который расшифровывается в существующий
   `click_id` того же workspace, и подписка пришла в пределах окна точной схемы.
   Побеждает всегда, независимо от других кандидатов.
2. `probabilistic` — детерминированного сигнала нет; берём клики этого канала в окне 72 ч и выбираем
   лучший по скору (§7).
3. `unattributed` — кандидатов нет.

Промежуточного «полу-точного» типа не бывает. Тип ровно один из трёх.

## 6. Точная схема (A)

```
клик → /r/{slug} → 302 → https://max.ru/<bot>?start=<click_id>
     → bot_started{payload=click_id, user_id=U}
     → бот показывает кнопку на канал
     → user_added{chat_id=C, user_id=U}
     → attribution(U,C) = click_id, type=deterministic, confidence=1.0
```

Связка идёт по `platform_user_id` — общему для `bot_started` и `user_added`. Это единственная
надёжная связь, которую даёт платформа.

Ограничения, известные заранее:
- payload ≤ 128 символов (FACT) → `click_id` 16 символов с запасом;
- клиенты старее iOS 2.7.0 / Android 2.9.0 диплинк-payload не поддерживают (FACT) → часть трафика
  придёт как `bot_started` без payload либо не придёт вовсе;
- `bot_started` документирован как «впервые или после остановки» → вернувшийся пользователь может
  не породить событие (`E4`). Если `E4` подтвердит проблему, обязательный fallback:
  бот отдаёт кнопку с `callback` и мы ловим `message_callback` — вторая попытка получить сигнал.

## 7. Вероятностная схема (Б)

Кандидаты: клики по каналу `C` в окне `[ts_sub − 72ч, ts_sub + 120с]`, не привязанные
детерминированно к другой подписке.

Скор кандидата `i`:

```
score_i = exp(−Δt_i / τ) × device_match_i × freshness_i
τ = 30 минут
Δt_i = ts_sub − ts_click_i (секунды, отрицательные → 0)
device_match_i = 1.0 если device_hint клика совпадает с платформой события, иначе 0.85
freshness_i = 0.6 если клик уже атрибуцирован к другой подписке (переиспользование), иначе 1.0
```

Победитель — `argmax(score)`.

```
confidence = score_top / Σ score_i
margin     = score_top / score_second   (при одном кандидате margin = ∞)
```

- `confidence` записывается как есть, диапазон (0, 1).
- `is_ambiguous = true`, если `margin < 1.2` **или** `confidence < 0.5`.
- Если кандидатов больше 20 в окне — канал считается «плотным»: `confidence` дополнительно делится
  на 2, `is_dense = true`. При плотном потоке честнее показать «источник неизвестен», чем угадать.

Все кандидаты сохраняются в `attribution_candidates` (JSON: click_id, score, Δt) — чтобы можно было
пересчитать задним числом и объяснить пользователю, откуда взялась цифра.

## 8. Конфликты

- Один клик — несколько подписок: возможно (человек подписался, отписался, подписался).
  Клик не «расходуется» сразу, но каждое повторное использование штрафуется `freshness = 0.6^n`,
  а после **пяти** привязок клик перестаёт быть кандидатом вовсе.
  Причина найдена на живых данных: в канале с органическим потоком единственный клик забирал себе
  всех, кто подписался в окне, и источник выглядел в десятки раз эффективнее, чем он есть.
  Один переход не приводит сорок человек — дальше это органика, совпавшая по времени.
- Одна подписка — несколько кандидатов: правило `argmax` + `margin` (§7).
- Детерминированный и вероятностный кандидаты одновременно: **детерминированный побеждает всегда**,
  вероятностный сохраняется в кандидатах для калибровки.
- Два `bot_started` с разными payload до одной подписки: побеждает **последний** по `ts_utc`,
  `is_ambiguous = true`.

## 9. Повторные подписки

- `user_added` по паре (`chat_id`, `platform_user_id`), для которой уже есть активная подписка,
  — дубль, игнорируем (idempotency, §11).
- Если между отпиской и новой подпиской прошло **менее 7 суток** — это `resubscribe`:
  новая запись подписки создаётся, но в когорту привлечения **не** попадает и в CPS не учитывается.
  Иначе источник, чьи подписчики «мигают», будет выглядеть лучше, чем он есть.
- Более 7 суток — полноценная новая подписка со своей атрибуцией.

## 10. Retention и стоимость живого подписчика

- Подписчик «жив на горизонте T», если на момент `ts_sub + T` у него нет `user_removed`
  с `reason = left`.
- `retention_T(source) = alive_T / cohort_size`, где когорта — атрибуцированные подписки источника.
- Горизонты: 24 ч, 7 д, 30 д.
- **Зрелость когорты**: подписки моложе `T` в знаменатель не входят. Если зрелых подписок меньше 20,
  метрика помечается `is_estimate = true` и в интерфейсе выводится как прогноз, а не факт.
- `CPS = spend / attributed_subscriptions`.
- **Живой CPS** = `spend / (attributed_subscriptions × retention_30d)`.
  Расход `spend` вводится вручную по источнику/кампании в MVP (импорт из рекламных кабинетов — не MVP).
- Подписки с `attribution_type = unattributed` не попадают ни в один источник, но **всегда**
  показываются отдельной строкой «источник неизвестен» с долей от общего числа. Эта доля —
  честный индикатор качества нашей собственной работы.

## 11. Идемпотентность

`idempotency_key` для входящего события:
`sha256(update_type | chat_id | user_id | timestamp | payload_hash)`.

Платформа не даёт собственного ID события (UNKNOWN), поэтому ключ синтетический. Риск: два *настоящих*
одинаковых события в одну миллисекунду будут схлопнуты — принимаем как допустимую потерю.

Правила:
- запись в `webhook_events` с уникальным индексом по `idempotency_key`; конфликт → 200 OK и выход;
- сырое тело запроса и заголовки сохраняются **до** разбора и никогда не удаляются;
- нормализация и атрибуция — отдельные шаги, идемпотентные по `raw_event_id`;
- ошибка обработки → статус `failed` + причина, событие остаётся для повторного прогона;
- пересчёт атрибуции возможен в любой момент из сырых событий, версия алгоритма пишется
  в `attribution.algo_version`.

## 12. Калибровка точности

Единственный честный способ узнать точность схемы Б — прогнать обе схемы на одном трафике.

Метод: на части трафика ставим redirect в режиме `bot` (даёт детерминированную истину), при этом
одновременно считаем, что предсказала бы схема Б для тех же подписок. Тогда

```
accuracy_Б = совпало(Б, A) / всего сравнимых подписок
```

Эту цифру, и только её, мы имеем право писать на сайте. До первого замера в маркетинге
не употребляется никакое число точности.

## 13. Что не входит в MVP

Мультиканальная атрибуция (first/linear/position-based), кросс-девайс склейка, атрибуция
до продажи, атрибуция Telegram. Модель данных должна позволять их добавить, логика — нет.
