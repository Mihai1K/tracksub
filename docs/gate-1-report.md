# Gate 1 — отчёт

Дата: 03.09.2026. Статус: **частично закрыт**. Документарная часть выполнена, экспериментальная —
заблокирована отсутствием доступа к платформе. Ниже по формату из протокола, п. 18.

---

## 1. Что проверено

- Документация `dev.max.ru`: разделы API (методы, объекты `Update`, `Chat`, `ChatMember`),
  `POST /subscriptions`, `GET /chats/{chatId}/members`, подготовка бота, диплинки, правила размещения.
- Модели данных официально проверенной командой MAX библиотеки `max-messenger/max-botapi-python`:
  `UserAdded`, `UserRemoved`, `BotStarted`, `Update`, `UpdateType`.
- Прошлые выводы этого проекта перепроверены против документации; расхождения зафиксированы.
- Собран измерительный стенд и прогнан на синтетических событиях: клик → редирект с `click_id` →
  `bot_started(payload)` → `user_added` → детерминированная атрибуция; дубль события отброшен;
  запрос с неверным секретом отклонён 403.

## 2. Что подтверждено

| | |
|---|---|
| **Диплинк с payload** | `https://max.ru/<botName>?start=<payload>`, до 128 символов; payload приходит в `bot_started`. Клиенты: iOS 2.7.0+, Android 2.9.0+ |
| **Подписки и отписки** | События `user_added` / `user_removed` существуют; `admin_id = null` отличает добровольный выход от удаления админом — retention считается корректно |
| **Ключ связи** | Общий `user.user_id` в `bot_started` и `user_added` — единственная надёжная связка |
| **Резервный контур** | `Chat.participants_count`, `Chat.participants` (map user_id → последняя активность), `GET /chats/{chatId}/members` (бот должен быть админом) |
| **Транспорт** | `platform-api2.max.ru`, токен только в заголовке `Authorization`, 30 rps, вебхук строго HTTPS/443 с сертификатом доверенного УЦ, секрет в `X-Max-Bot-Api-Secret` |
| **Доступ** | Юрлица, **ИП и самозанятые** — резиденты РФ; бот проходит модерацию |

**Главный подтверждённый факт, определяющий продукт:** в `user_added` нет идентификатора ссылки,
payload или источника. Поля: `inviter_id?`, `chat_id`, `user`, `is_channel`.
Детерминированная атрибуция «подписка → рекламная ссылка» через события канала **невозможна**.
Механика TGTrack в MAX не воспроизводится ни при каком старании.

## 3. Что не подтверждено

Экспериментальная часть Gate 1 не выполнена: у нас нет верифицированного профиля партнёра MAX,
токена бота и домена с доверенным сертификатом. Без них следующее остаётся открытым:

1. **E1 — приходит ли `user_added` при самостоятельной подписке на публичный канал.**
   Формулировка документации «добавлен или перешёл по ссылке» допускает оба прочтения.
   Если нет — вероятностной схемы не существует вовсе.
2. **E4 — приходит ли `bot_started` повторно.** Документация: «впервые или после остановки».
   Если для вернувшегося пользователя события нет — точная схема дырявая, нужен fallback
   через кнопку и `message_callback`.
3. Задержка и надёжность доставки, политика ретраев MAX, живучесть подписки при простое.
4. Пригласительные ссылки канала: количество, поведение при обновлении, наличие статистики.
   В Bot API методов для них не найдено вообще.
5. Пагинация и применимость `GET /chats/{chatId}/members` к крупным каналам.
6. Пройдёт ли бот такого назначения модерацию.

Опровергнуто из прошлых выводов проекта: «только ИП и юрлица» (самозанятые тоже могут);
«5 ботов на организацию» (документация говорит лишь, что лимит зависит от типа профиля);
«вебхук отключается через 8 часов недоступности» (в текущей документации не найдено).

## 4. Что является риском

| Риск | Влияние | Митигация |
|---|---|---|
| E1 = нет | Схема Б мертва; остаётся только бот-прокладка с потерей 20–50% конверсии. Оффер и юнит-экономика меняются | Эксперимент до любой разработки |
| E4 = нет | Часть трафика неатрибуцируема даже в точной схеме | Fallback на `message_callback`, проверяется тем же экспериментом |
| Модерация не пропустит бота | Продукта нет | Подать бота на модерацию первым действием, до кода |
| Точность схемы Б окажется низкой | Продукт продаёт «источники», а показывает угадайку | Калибровка A↔Б на общем трафике (`attribution.md` §12); публиковать только измеренное число |
| Платформа закроет дыру сама (свой рекламный кабинет обещан к концу 2026) | Обесценивание | Ценность держать в кросс-источниковом отчёте, retention и выгрузке во внешние системы |
| ПДн-контур | Блокер публичного запуска | Оферта с поручением обработки, уведомление РКН, БД в РФ |

## 5. Что предлагаю сделать

**Не начинать Gate 2.** Сначала — три действия, которые не требуют ни строчки продуктового кода:

1. Оформить/подтвердить профиль партнёра MAX (годится самозанятость — это дешевле и быстрее ИП,
   но проверить ограничения по числу ботов для этого типа профиля) и создать бота.
2. Подать бота на модерацию **сегодня** — это самый длинный лид-тайм и одновременно проверка гипотезы
   «нам вообще разрешат такой продукт».
3. Прогнать `docs/gate-1-experiment.md`, E1–E8. Полтора–два часа работы, когда доступ будет.

Параллельно — 14-дневный тест спроса из предыдущего разбора. Он не зависит от техники и может
идти в тех же днях.

Архитектурное решение зафиксировано в `docs/architecture.md`: платформо-нейтральное ядро,
`PlatformAdapter` на входе, `ConversionProvider` на выходе, сырые события как система записи,
атрибуция — отдельный версионируемый слой. MAX — первая реализация адаптера, Telegram — вторая,
без переписывания ядра.

## 7. Как проверить результат

```bash
node --check probe/*.js                 # синтаксис
cp .env.example .env                    # заполнить MAX_BOT_NAME, секрет
set -a && . ./.env && set +a
node probe/server.js                    # в отдельном окне
curl -i "http://localhost:8080/r/bot?utm_source=test"   # 302 на max.ru/<bot>?start=<click_id>
node probe/report.js                    # сведение
```

Прогон на синтетике уже выполнен: атрибуция сошлась, дубль отброшен, неверный секрет отклонён.
Достоверность этого прогона равна нулю в части реального поведения MAX — он проверяет только стенд.

2. Решение по типу профиля партнёра: самозанятый или ИП. Влияет на лимит числа ботов и на то,

   останется бот-прокладка с потерей четверти конверсии — мы всё ещё делаем этот продукт?
