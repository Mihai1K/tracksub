# Архитектура: решение Gate 1

Одностраничное решение, принятое по итогам изучения API. Детализируется на Gate 2, не раньше.

## Главное ограничение, из которого всё следует

`user_added` не содержит ни ссылки, ни payload, ни источника (FACT, см. `max-api-findings.md` §3.1).
Единственный ключ связи между «переходом» и «подпиской» — **`platform_user_id`**, и он появляется
только если пользователь прошёл через бота. Значит:

- источник живёт **на нашей стороне** (redirect + `click_id`), а не на стороне платформы;
- атрибуция — отдельный слой, а не поле в таблице подписок;
- для части трафика правильный ответ — «источник неизвестен», и это надо уметь показывать.

## Слои

```
Tracking (redirect, click_id, UTM)
        │
Event Collector      ← адаптеры платформ: MaxAdapter, [TelegramAdapter]
        │              принимает сырое, ничего не интерпретирует
Raw Event Store      ← system of record, ничего не удаляет
        │
Event Normalizer     ← платформенное → доменное: Subscribe / Unsubscribe / BotStart
        │
Attribution Engine   ← чистая функция над нормализованными событиями + кликами
        │              версионируется, пересчитывается из сырого в любой момент
Analytics Core       ← когорты, retention, CPS, живой CPS
        │
Conversion Dispatcher ← провайдеры выгрузки: YandexMetrika, [YandexDirect], [VkAds]
        │              очередь, ретраи, статус доставки
External Ad Platforms
```

## Два интерфейса, которые нельзя размывать

**`PlatformAdapter`** — вход. `verify(request)`, `parse(raw) → NormalizedEvent[]`, `identity(event) → PlatformUser`.
MAX — первая реализация, Telegram — вторая, без переписывания ядра.

**`ConversionProvider`** — выход. `supports(kind)`, `send(batch) → DeliveryResult`, `status(id)`.
Метрика — первая реализация. Если за MVP не успеваем полноценную отправку — остаётся интерфейс
и провайдер-заглушка, **явно помеченный как не отправляющий**. Имитации работающей интеграции быть не должно.

## Правила, которые дороже нарушить, чем соблюсти

1. Сырое событие сохраняется **до** любой обработки и не удаляется никогда.
2. Атрибуция не пишется в подписку «на месте» — это отдельная запись со своим `algo_version`,
   типом, уверенностью и списком кандидатов. Пересчёт не теряет историю.
3. Идемпотентность на входе (ключ из `attribution.md` §11) и на каждом шаге конвейера.
4. Нормализованные события платформенно-нейтральны: в `Analytics Core` не должно быть слова `max`.
5. Всё время — UTC в хранении, таймзона workspace — только на отображении.

## Данные (ядро)

`Workspace` → `Channel` (platform, external_chat_id) → `TrackingLink` → `Click`
`PlatformUser` (platform, external_user_id, уникальность в паре)
`SubscriptionEvent` / `UnsubscriptionEvent` → `Attribution` (type, confidence, candidates, algo_version)
`WebhookEvent` (raw, headers, idempotency_key, status) — вход
`Conversion` (attribution_id, provider, status, attempts) — выход
`DailyMetric` — витрина, всегда пересчитываемая из фактов

## Что осознанно не проектируем сейчас

Мультиканальную атрибуцию, кросс-девайс, воркспейс-роли сложнее «владелец/участник», биллинг,
мультитенантные ограничения производительности. Модель данных им не мешает; логики нет.
